# Stripe / STARDUST First Phase

## Database

The base tables have been created manually by the owner. Run only
`supabase/stardust-functions.sql` next, in the Supabase SQL Editor.
It installs atomic financial functions, restricts them to `service_role`, and
removes the obsolete `extend_ai_entitlement` function. It does not delete old
orders or payment records. `supabase/stardust.sql` is the full migration for a
fresh installation; do not run the old `supabase/ai-access.sql` for this system.

Before launch, set `stardust_settings.launch_at` to the actual agreed launch
time, before issuing any production free allowances. Changing this time after
allowances have been issued requires a separate reconciliation migration.

## Environment

- Existing Supabase server configuration, including `SUPABASE_SECRET_KEY`.
- `STRIPE_SECRET_KEY`: use a Stripe test key during validation.
- `STRIPE_WEBHOOK_SECRET`: use the secret for the matching test endpoint.
- `NEXT_PUBLIC_SITE_URL`: trusted canonical origin for Checkout redirects.
- `STARDUST_CHECKOUT_ENABLED=false`: default; gates top-ups, membership
  purchases and STARS-funded readings. Free/member allowances remain usable.
- `CRON_SECRET`: long random value, only for the maintenance endpoint.
- Existing `RESEND_API_KEY` and `CONTACT_FROM_EMAIL` for transactional mail.

Never expose Stripe secrets or the Supabase administrative key in NEXT_PUBLIC
variables. No Stripe subscription or WeChat Pay integration is used.

## Stripe Endpoint

### Local Acceptance With The Same Supabase Project

Stripe test keys now select the separate `stardust_sandbox` schema for all
financial records, allowances and reports. Live keys select `public`. There is
no fallback from a missing sandbox schema to the live ledger. Signed webhook
events with the wrong `livemode` are rejected before any database mutation.
Sandbox maintenance never sends queued email to real account addresses.

1. Run `supabase/stardust-sandbox.sql` manually in Supabase SQL Editor.
2. In Supabase Data API settings, add `stardust_sandbox` to Exposed schemas.
   Keep all existing entries, including `public` and `tarot` if present.
3. Keep `STRIPE_SECRET_KEY` as a test key and the site origin as localhost.
4. Run `node scripts/install-stripe-cli.mjs` if the temporary CLI is absent.
5. Run `node scripts/stripe-listen.mjs` in a separate WSL terminal and keep it
   open. It uses the test key without putting it in command-line arguments,
   synchronizes the CLI signing secret to `.env.local`, and privately backs up
   the previous secret in a restricted temporary directory. It never enables
   Checkout. Forwarder logs redact signing secrets and API keys. The listener
   uses `--latest` so old account API defaults do not omit required fields.
6. `node scripts/verify-stripe-local.mjs` checks the test key and local signature
   configuration without creating a payment or modifying account balances.
   This verification alone does not prove event forwarding.
7. Only after the sandbox schema and listener are ready, set
   `STARDUST_CHECKOUT_ENABLED=true` locally, reload/restart the development
   server as necessary, and use an authenticated test account in `/wallet`.
   Alternatively `node scripts/check-billing-sandbox.mjs --enable` verifies
   read access to all ten sandbox tables, refuses live keys or non-local
   origins, and enables only the local environment flag. It does not create
   orders, payments or wallet credits. Run without `--enable` for read-only
   checks that leave the environment file unchanged.
8. Use Stripe's test card `4242 4242 4242 4242`, a future expiry date and a test
   CVC. Confirm that the paid event returns HTTP 200 and the sandbox wallet
   receives exactly one credit, including after a webhook resend.

Never replace the test key with a live key to resolve a testing issue. Before
live launch, configure the actual production webhook secret and turn off
Checkout until live readiness has been separately approved. Test ledger data
must never be copied into the public financial tables.

The sandbox migration is generated by `node scripts/build-billing-sandbox.mjs`
from the complete public migration. Its SQL uses its own schema and preserves
public financial data. Re-running it does not reset existing sandbox balances.

Endpoint: `/api/stripe/webhook`

Subscribe to:

- `checkout.session.completed`
- `checkout.session.async_payment_succeeded`
- `checkout.session.async_payment_failed`
- `checkout.session.expired`
- `charge.refunded`
- `charge.dispute.created`

Checkout supports card and Alipay in AUD, subject to the account's enabled
payment methods. The fixed top-ups are A$10,25,50,100,200,500; A$1 = 100 STARS.
Only a verified paid webhook credits the wallet, never a browser redirect.
Refunds/disputes block spending for manual review; they do not automatically
claw back potentially spent balances or decide statutory refund rights.

## Scheduled Maintenance

An external scheduler must GET `/api/billing/maintenance` with
`Authorization: Bearer <CRON_SECRET>`. Schedule daily, preferably more often
for prompt release of abandoned holds and mail retries. This repo does not
automatically create a hosted cron job. Reminder dates use Australia/Sydney.
Mail is queued transactionally and sent by Resend; no marketing is included.
Without mail credentials the queue is retained, not marked delivered.

## Routes

- `/pricing`: public membership and top-up catalogue.
- `/wallet`: signed-in balances, allowances, purchases and saved reports.
- `/admin/billing`: admin-only latest 100 top-up orders.
- `/learn/waite`, `/learn/thoth`, `/learn/astrology`: authorized course videos.

In existing video management, use categories `course-waite`, `course-thoth`,
`course-astrology`. Private signed URLs are issued only after checking the
matching course entitlement or an active annual membership. Unfiltered public
video lists exclude these categories. Published non-course videos keep their
existing access behavior. Individual course purchases are deliberately not
enabled until course content is confirmed ready.

## Charging And Deferred Work

Waite non-single spreads cost 300 STARS; Thoth spreads cost 100. The free
21-reading program and annual allowances are shared tarot allowances, consumed
by earliest expiry. Admin readings do not consume allowances or STARS.
Unconfirmed single-card/natal/synastry/numerology prices cannot debit STARS.
Natal and synastry readings can consume the appropriate membership allowances.
The Thoth report remains the existing local card-meaning report, not a new AI.

Annual and monthly memberships are independent. Renewals issue new allowances
immediately and extend active same-plan batches. Expired batches are not
revived. Free batches still expire at the end of each Sydney calendar month.

Not yet implemented: invitation attribution/rewards; product checkout and
shipping; email-reading fulfillment; consultant calendars, booking/refunds
and Zoom booking linkage; numerology charging; standalone course purchases.
Their prices/allowances in the requirements are not evidence of a completed
fulfillment system. Keep production purchasing disabled until promised member
services and course content are ready, tested and operationally supported.

Before accepting live payments, confirm the stored-value and service model
with Stripe and obtain appropriate legal/accounting review.

## Verification

- `node tests/stardust.test.mjs`

The isolated SQL tests require a temporary PGlite installation at
`/tmp/zblog-billing-test`, or a `PGLITE_MODULE` path to its `dist/index.js`.
They do not use the remote Supabase database or make real Stripe payments.

delayed webhooks, refunds/disputes, authenticated account isolation, and mail
delivery with actual test-account credentials.
